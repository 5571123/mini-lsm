# 阶段 Ⅰ 扩展指南：鉴权层与 WAL 加密

本文件说明怎样在**不改动 LSM 核心**的前提下，给 Mini-LSM 加两个上层模块：
用户鉴权与 WAL 加密。所有改动都落在「引擎外侧」或「IO 编解码边界」，不动压缩、读路径与
SST 文件格式。

## 0. 红线：什么算「LSM 核心」

| 目录 / 文件 | 是否可改 | 说明 |
| --- | --- | --- |
| `table.rs`、`table/*` | 不改 | SST 文件格式与块读取 |
| `block.rs`、`block/*` | 不改 | 块编码与迭代 |
| `compact.rs`、`compact/*` | 不改 | 压缩策略与执行 |
| `iterators/*`、`lsm_iterator.rs` | 不改 | 归并迭代器 |
| `lsm_storage.rs` 的读路径 / 冻结 / 落盘 | 不改逻辑 | `get`/`put`/`scan`/`force_flush` 的实现不动 |
| `manifest.rs` | 不改格式 | 清单只记元信息，不承载用户数据 |
| **`wal.rs`** | **可改（本阶段唯一允许改的核心文件）** | 它是 WAL 的编解码边界，改它不影响 LSM 语义 |
| 新增 `auth.rs` / `crypto.rs` | 可加 | 引擎外侧的装饰层 |

判断标准：**改动不能改变 SST 文件的字节格式，也不能改变「谁赢」的语义**（同一个 key 谁更新）。
鉴权与加密都是「进去之前 / 出来之后」的事，符合这个标准。

## 1. 鉴权层

### 1.1 放哪里

`MiniLsm` 的公开 API 是 `open / get / put / delete / write_batch / scan / sync / close`
（`mini-lsm/src/lsm_storage.rs`）。做法是在它外面包一层，**不要**把权限判断塞进
`LsmStorageInner`：`LsmStorageInner` 没有「当前用户」这个概念，塞进去会污染压缩线程与
后台落盘的调用路径。

```
用户代码
   │  login(user, password) -> Session
   ▼
AuthEngine            <- 你新增的模块：权限检查 + 键前缀改写
   │  put(uid, key, value) -> MiniLsm::put(uid ‖ key, value)
   ▼
MiniLsm / LsmStorageInner（原封不动）
```

### 1.2 用前缀键做命名空间隔离

每个用户的数据写在自己的前缀下，物理上共用一个引擎：

```rust
/// 用户数据统一加上 8 字节大端 uid 前缀，系统元数据用 0x00 前缀，保证不会和用户键冲突。
fn user_key(uid: u64, key: &[u8]) -> Vec<u8> {
    let mut out = Vec::with_capacity(8 + key.len());
    out.extend_from_slice(&uid.to_be_bytes());
    out.extend_from_slice(key);
    out
}
```

系统表（用户表、口令哈希）放在同一引擎的 `b"\x00sys/users/"` 前缀下，启动时加载。

### 1.3 扫描必须夹紧范围

这是最容易漏的一处：`scan(lower, upper)` 的边界是**用户视角的键**，必须换成前缀内的物理键，
否则 A 用户能扫到 B 用户的数据。

```rust
// 上界为无界时，用「前缀 + 0xFF…」作为该用户命名空间的右边界。
fn prefix_upper(uid: u64) -> Vec<u8> {
    let mut out = Vec::with_capacity(9);
    out.extend_from_slice(&uid.to_be_bytes());
    out.push(0xFF);
    out
}
```

* `lower = Included/Excluded(user_key(uid, lower))`
* `upper = 有界 → user_key(uid, upper)`；`Unbounded → Included(prefix_upper(uid))`

写测试时至少覆盖：空 prefix 扫描、`[a, b)` 半开区间、跨用户不可见、删除标记（墓碑）不会被
`scan` 输出。

### 1.4 口令与令牌

* 存储：`salt(16B) ‖ sha256(salt ‖ password)` 就够教学用；生产应换 Argon2id，并在文档里写明理由。
* 会话令牌：登录后返回随机 32 字节令牌，`Session { uid, token, expire_at }` 存内存表（重启失效）。
* 权限模型：`Role { ReadOnly, ReadWrite, Admin }`，在 `AuthEngine` 的入口函数里做匹配，
  **失败要返回 `anyhow::Error` 而不是 panic**。

### 1.5 验收

1. 未登录调用任何数据接口 → 报错，不写盘；
2. A 用户 `scan(None, None)` 只能看到自己的键；
3. 只读用户 `put` 失败，但 `get`/`scan` 正常；
4. 删除用户后其数据仍可被 admin 扫描到（数据保留，不级联删除，若要级联删除需在文档里声明）。

## 2. WAL 加密

### 2.1 现在的记录格式

`mini-lsm/src/wal.rs` 里每条记录的布局（大端）：

```
┌──────────┬─────┬────────────┬───────┬──────────┐
│ key_len  │ key │ value_len  │ value │ crc32    │
│ u16 (2B) │     │ u16 (2B)   │       │ u32 (4B) │
└──────────┴─────┴────────────┴───────┴──────────┘
crc32 覆盖它前面的全部字节
```

`Wal::recover` 顺序解析：边读边算 `valid_len`，遇到「剩余字节不够一条完整记录」就跳出循环，
最后 `set_len(valid_len)` 把损坏的尾部截掉 —— 这保证了崩溃只会丢掉最后一条未写完的记录。

### 2.2 加密后的格式

只在**整条记录**外面套一层，明文部分保持原样，这样 `MemTable` 与 `LsmStorageInner` 完全无感：

```
┌───────────┬───────────┬──────────────┬────────────────────────┐
│ magic u16 │ frame_len │ nonce (12B)  │ AEAD 密文（含 16B tag）│
│ 0xE1A5    │ u32 (4B)  │ 每条随机      │  = 加密后的旧格式记录   │
└───────────┴───────────┴──────────────┴────────────────────────┘
frame_len 指 nonce + 密文的长度
```

`magic` 用来区分明文旧库与加密新库，方便 `recover` 走不同分支。

### 2.3 要改的函数

| 函数 | 改什么 |
| --- | --- |
| `Wal::put` / `Wal::put_batch` | 先把明文记录编好（含 crc32），再用 `ChaCha20Poly1305::encrypt` 加密，先写头（magic、frame_len、nonce）再写密文 |
| `Wal::recover` | 先读头，按 `frame_len` 判断剩余字节够不够 → 不够就 break（保持「只丢最后一条」的语义）；够就解密，解密失败要区分「密钥错」（直接报错）与「尾部损坏」（截断） |
| `Wal::create` / `Wal::recover` 的打开方式 | 需要读密钥，见 2.4 |
| `Wal::sync` | 不变 |

`crc32` 可以保留（解密后再校验，作为额外保险），也可以删掉用 AEAD tag 代替 —— 教学上建议保留，
这样「解密失败」和「内容被改」两类错误可以分开演示。

### 2.4 密钥从哪来（两条路，选一条并写进文档）

* **方案 A（零侵入，推荐）**：密钥在 `wal.rs` 内部从一个 `OnceLock<[u8; 32]>` 读，
  首次由 `MINI_LSM_WAL_KEY`（64 位 hex）环境变量初始化。`lsm_storage.rs` 一行都不用改。
* **方案 B（小改）**：给 `LsmStorageOptions` 增加 `wal_encryption_key: Option<[u8; 32]>`，
  沿 `MemTable::create_with_wal` 传进 `Wal`。更干净，但要动核心结构体，会脱离上游 diff。

无论哪条路，密钥**都不能**写进代码或提交到仓库；`.env.example` 只放占位符。

### 2.5 四个坑

1. **截断逻辑依赖长度前置**：加密后密文长度对不上明文，必须把 `frame_len` 放在头里，
   不能用「读 u16 得到 key 长度」的方式推算边界。
2. **不能用固定 nonce**：同一密钥复用 nonce 会让 AEAD 彻底失效（可恢复明文异或关系）。
   每条记录用 `rand::rng().fill(&mut nonce)` 生成。
3. **密钥轮换**：本阶段不做，但要在文档里写明「换密钥等于旧 WAL 不可恢复」，因为 WAL 存活
   周期很短（落盘后即删），实际影响仅限未落盘数据。
4. **`set_len` 截断尾部之后要 `seek(End(0))`**：Windows 下这一步不做，后续追加会写错位置
   （本仓库已经修过这个坑，见 `Wal::recover` 里的注释）。

### 2.6 验收

1. 加密写入 3 条记录 → 关闭 → 重新打开，数据完整；
2. 手动改密文里任意 1 个字节 → recover 报错（不能 panic，也不能静默返回脏数据）；
3. 把 WAL 尾部截掉 5 个字节 → 恢复出前 2 条，文件被截断到第 2 条末尾；
4. 用错误密钥打开 → 明确报「密钥错误」，而不是当成脏数据丢掉；
5. `cargo test -p mini-lsm` 仍然全绿（说明没碰坏核心语义）。

cargo check --workspace --all-targets

cargo test -p mini-lsm-mvcc     # 96 个测试
python scripts/sync_shared_files.py --check   # 改过共享文件时要先同步

改动的 diff 里如果出现 `table.rs` / `compact/*` / `block/*` / `iterators/*`，先停下来想一想：
这个需求真的必须在核心层做吗？绝大多数情况可以在 `AuthEngine` 或 `wal.rs` 里解决。
